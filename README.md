## 1. Гурван сценарио (6 хэсэгтэй формат)

| Хэсэг | Performance — `/cart/add` | Reliability — `/pay` | Availability — сервер унах |
|---|---|---|---|
| **Тойм** | Хэвийн ачаалалд сагсанд нэмэх хурдан байх | Төлбөрийн хүсэлт ихэнхдээ амжилттай байх | Сервер унаад сэргэхэд үйлчилгээ хүлээн зөвшөөрөгдөх түвшинд байх |
| **Системийн төлөв** | Ажиллаж буй, дулаан (warm) | Ажиллаж буй, gateway ~5% алдаатай | Ажиллаж байгаад гэнэт зогсоно |
| **Орчны төлөв** | 20 VU тогтмол, ~15 давталт/с (VU бүр 1 давталт/≈1.3с) | 20 VU, ~15 төлбөр/с, 1 мин | 20 VU, 2 мин, дунд нь 10с зогсолт |
| **Гадаад өдөөлт** | Хэрэглэгч `POST /cart/add` | Хэвийн хэрэглэгчийн `POST /pay` | Процесс crash (Ctrl+C), 10с дараа дахин асаах |
| **Шаардлагатай хариу** | 200 + JSON `{ok:true}` | 200 `{paid:true}`; алдаа бол 500 + тайлбар | Сэргэсний дараа хүсэлтүүд дахин 200 |
| **Хэмжүүр** | p95 latency < 50 мс | error rate < 8% (POFOD ≈ 0.05) | хүсэлтийн амжилт ≥ 90%, сэргэх хугацаа ≤ 10с |

Нэмэлт (4-р) сценарио: `/report` p95 < 450 мс (сервер 200–400 мс унтдаг).

## 2. SLO

| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency | **p95 < 50 мс** | 20 VU, 1 мин |
| Reliability | `/pay` error rate | **< 8%** | 20 VU, 1 мин |
| Availability | бүх check-ийн амжилтын хувь | **≥ 90%** | 2 мин, 10с зогсолттой |
| Report (нэмэлт) | `/report` latency | **p95 < 450 мс** | 20 VU, 1 мин |

Босгоны үндэслэл:
- **50 мс** — localhost дээр `/cart/add` 1–5 мс хариулдаг тул 200 мс юу ч хэмжихгүй; 50 мс нь хэвийн үед хангалттай зай үлдээж, бодит удаашралыг барина.
- **8%** — серверт 5% алдаа суулгасан тул санамсаргүй хэлбэлзэлд 3 пунктын зай.
- **90%** — 2 минутад 10с зогсолтыг (≈8%) даах хэмжээ.
- **450 мс** — sleep дээд тал 400 мс + сүлжээ/event loop-ийн 50 мс.

**Error budget (цагаар):** 2 мин × (1 − 0.90) = **12 секунд** зогсох эрх.

## 4. Mini chaos — `results/chaos.txt`

`DURATION=2m k6 run slo-test.js` ажиллаж байхад 45 дахь секундэд серверийг kill хийж, 10с дараа дахин асаасан ([chaos.sh](chaos.sh)).

| Threshold | Үр дүн |
|---|---|
| `checks` rate>0.90 (availability) | **✗ 87.22%** (4951 / 5676) |
| `http_req_failed{name:pay}` rate<0.08 (reliability) | **✗ 16.12%** |
| `http_req_duration{name:cart}` p(95)<50 | ✓ 1.39ms |
| `http_req_duration{name:report}` p(95)<450 | ✓ 396.3ms |

- **Бодит availability (хүсэлтээр):** 4951 / 5676 = **87.22%** → SLO (90%) зөрчигдсөн, k6 exit 99.
- **Error budget (хүсэлтээр):** 5676 × 10% = 567 хүсэлт; бодит алдаа `http_req_failed` = 725 → budget хэтэрсэн.
- **Яагаад цагийн budget-ээс зөрөв:** 10с зогсолт нь 2 минутын 8.3% тул цагаар 12с-ийн budget-д багтана. Гэвч зогсолтын үед хүсэлт `connection refused`-ээр агшин зуур буцаж, `/report`-ын 200–400мс хүлээлт алга болдог тул тэр 10 секундэд хэвийнээс олон хүсэлт (бүгд алдаа) явсан — хүсэлтийн хувь цагийн хувиас муу гарна.
- **Reliability мөн FAIL:** унасан үед `/pay` бүр алддаг тул нэг эвдрэл хоёр SLO-г зэрэг зөрчсөн. Тусгаарлахын тулд reliability SLI-г зөвхөн серверээс ирсэн хариунд (`status != 0`, жишээ нь 5xx / нийт хариу) тооцож, холболтын алдааг availability-д үлдээж болно.
